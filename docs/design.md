# 新作者成长识别：领域设计

## 1. 背景与问题

运营团队观察到两类系统性误判：

- **小圈层专业作者被漏掉**：入驻不到一年，在小圈层里持续被用户主动推荐，但粉丝基数小，按绝对量口径的统一扶持名单永远轮不到他们。
- **热点型账号被误判**：靠一次热点暴涨进入视野，随后迅速沉寂，单次峰值被当成了成长。

本产品的目标：以**统计窗口**为单位沉淀作者成长信号，在**同领域基准**下比较，识别**跨窗口持续成长**的新作者；全过程**可审计、可重现、可复核、可申诉**。

## 2. 设计原则

1. **窗口化**：一切信号按统计窗口（周）聚合保存，窗口关闭后冻结，只读不改写。
2. **领域归一**：领域规模不同，指标先与同期同领域基准比较（分位），再谈跨领域比较。
3. **追加式历史**：删除作品、异常流量、账号合并、规则换版都以追加记录处理，历史判断保持原样。
4. **名单可重现**：每期名单绑定数据快照与规则版本，同一快照 + 同一规则版本必得同一名单。
5. **机器初筛、人做决定**：反作弊与人工复核是名单生效的前置环节，各自留痕。
6. **作者有限透明**：作者可见影响自身的主要依据并申诉，不可见他人私密数据。

## 3. 记录类型

| 记录类型 | 内容 | 关键约束 |
| --- | --- | --- |
| 作者档案 | 起始时间、所属领域、当前流程状态 | 起始时间以首个公开作品为准，入驻 ≤ 365 天才进入新作者池 |
| 作品信号 | 作品主题、原创状态、有效观看、主动推荐、负反馈 | 单作品粒度，是窗口聚合的输入 |
| 统计窗口 | 上述信号按作者 × 窗口的聚合 | 关闭后冻结；修正走追加记录 |
| 领域基准 | 每领域每窗口的指标分布（分位） | 与窗口同期，版本化保存 |
| 候选结论 | 是否候选、主要依据、归一化指标值 | 必须绑定 `snapshot_id` 与 `rule_version` |
| 反作弊结论 | 刷量、搬运、异常流量等机器判定 | 名单生效前置；细节不对作者公开（防绕过），只告知结论类别 |
| 复核意见 | 人工复核结论与理由 | 复核人、时间、结论留痕 |
| 扶持动作 | 流量扶持、活动邀约等 | 按窗口记录，是效果评估的输入 |
| 效果评估 | 扶持前后多窗口的持续创作与受众留存对比 | 见第 9 节 |
| 申诉记录 | 作者申诉与再复核结论 | 追加保存，不改写原候选结论 |
| 数据快照 | 某期名单的完整输入：窗口清单、基准版本、规则版本与参数、评分明细 | 发布后不可变 |
| 账号血缘事件 | 账号合并/拆分 | 历史记录不改属主，消费方按血缘解析 |

## 4. 统计窗口与信号口径

- 窗口以周为单位，关闭时间固定；关闭后聚合结果冻结。
- **有效观看** = 原始观看 − 被隔离的异常流量。隔离依据以调整记录留痕，不回改原始计数。
- **主动推荐**（用户主动分享/推荐）是核心正向信号，比被动曝光更能反映认可；**负反馈**（不感兴趣、举报等）与**原创状态**作为门槛条件，而非加分项。

## 5. 领域归一化

- 每个窗口为每个领域计算基准分布（如主动推荐率 = 主动推荐 / 有效观看 的分位数）。
- 作者指标一律先换算为**同领域同期分位**，再参与候选规则。小领域作者不因绝对量小被埋没，大领域作者也不因体量天然占优。
- 基准本身版本化（`benchmark_version`），候选结论记录所用版本，保证可重现。

## 6. 历史不可改写：四类事件的处理

| 事件 | 处理方式 |
| --- | --- |
| 删除作品 | 记录删除事件；已关闭窗口的聚合不变，未关闭窗口在关闭时按当时可见作品聚合 |
| 异常流量 | 隔离为调整记录；窗口已关闭后才发现的，追加窗口修正记录并触发必要的复审，不改原窗口 |
| 账号合并 | 写入账号血缘事件；历史记录保持原属主，合并前历史是否计入新账号由当期规则版本决定并留痕 |
| 规则换版 | 规则带版本号与生效窗口范围；新版只作用于新窗口，已发布结论不回溯 |

## 7. 候选产生：持续成长，而非单次暴涨

候选规则（示例，参数属规则版本的一部分）：

- 入驻 ≤ 365 天；
- 最近 8 个窗口中 ≥ 6 个窗口，主动推荐率处于同领域前 20%；
- 原创比例 ≥ 阈值，负反馈率 ≤ 阈值。

**暴涨识别**：单窗口指标相对作者自身前序中位数出现尖峰、且随后窗口回落的，标记为"热点型"，不进入候选，转回观察中。成长结论必须跨多个窗口持续成立。

## 8. 反作弊与人工复核

流程状态机：

```
观察中 → 候选 → 待复核 → 已入选 → 扶持中 → 已结束
              ↑________申诉中________┘
```

- 候选先过机器反作弊（刷量、搬运、异常流量），再交人工复核；两个环节的结论分别落为**反作弊结论**与**复核意见**记录。
- **申诉中**可由候选、待复核、已入选进入；复核完成后回到原流程或已结束，申诉与再复核结论追加保存。

## 9. 扶持效果评估

- 以扶持动作为分界，对比前后各 M 个窗口：
  - **持续创作**：活跃窗口占比、原创作品产出；
  - **受众留存**：回访观众占比、老观众贡献观看占比、负反馈变化。
- 结论分级为持续成长 / 持平 / 回落。**单次涨粉不是成长结论**——评估只看跨窗口的持续表现。

## 10. 数据快照与名单重现

每期名单生成时落一份**数据快照**：输入窗口清单、领域基准版本、规则版本与参数、候选评分明细（含归一化值）。快照发布后不可变。运营可用同一快照 + 同一规则版本重放，得到与原名单一致的结果，用于审计与争议处理。

## 11. 作者透明与数据权限

- **作者视图**：自身各窗口主要指标、同领域分位、入选或未入选的主要依据、申诉入口。
- **不可见**：其他作者的任何数据；反作弊内部规则细节（只告知结论类别，防止绕过）。
- **运营/复核**：按角色访问候选相关数据；对外公示名单只含必要信息。

## 12. 与公开资料契约的对应

`fixtures/domain.json` 是本设计的公开样例：`record_types` 列出第 3 节全部记录类型，`workflow_states` 列出第 8 节状态机，`facts` 记录关键业务事实，`sample` 展示一个带窗口信号、领域基准、快照与规则版本的作者样例。`contracts/domain.schema.json` 与 `domain_context/loader.py` 对关键记录类型与流程状态做了强制校验，后续服务应继续兼容。
